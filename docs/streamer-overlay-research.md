# 主播自用弹幕悬浮窗方案调研

> 历史调研记录。用户已决定直接接入最新版，当前实现已切换到 chat-overlay 1.1.1 / master f940914，不迁移旧配置。实现状态见 [新版接入说明](chat-overlay-integration.md)。


日期：2026-10-09。目标：主播在直播时自己阅读弹幕；集成到锤子，尽量减少开发、维护和用户配置成本；沿用 Windows/macOS 的 Electron 应用及已经接入的 LAPLACE 事件源。

结论：在现有项目条件下，继续使用当前锁定的 chat-overlay 显示实现，短期总成本最低。没有发现一个可以直接替换、同时明显降低跨平台集成成本的候选。上游最新版值得参考功能，但直接升级不省适配成本；需要大幅定制时再考虑将当前实现收敛成内部显示模块，不必仅为移除子模块而重构。

## 当前真正复用的部分

锤子自己负责 Electron 窗口、置顶、穿透、关闭、位置保存和内容保护；chat-overlay 提供消息列表、设置界面、自动滚动及 Event Bridge SDK 订阅。

当前核心渲染器约 585 行，样式约 495 行，已经有针对消息保留、滚动和穿透决策的 5 个测试。子模块独立应用的主进程、打包和发布配置没有被作为锤子的运行入口。

数据流是：LAPLACE 控制台采集事件 → 锤子本地 WebSocket 事件桥 → 悬浮窗。复用同一事件流也方便点歌机等功能，不需要悬浮窗维护另一套 B站认证和弹幕协议。

## 为什么成熟网页方案也不是直接替换

blivechat 的 [`ChatClientRelay.js`](https://github.com/xfgryujk/blivechat/blob/dev/frontend/src/api/chat/ChatClientRelay.js) 使用 `/api/chat` 和 `{cmd, data}` 协议，弹幕内容采用自己的消息模型；锤子 Event Bridge 使用 LAPLACE 事件对象及角色子协议。两者不能只改服务器地址就互通。

如果只是复用它的评论栏，需要适配事件格式、设置、Vue 渲染入口和样式，仍需自己实现桌面窗口操作。若使用完整后端，则还要管理 Python 服务或公共服务器，并增加独立连接和配置链路。官方 README 当前线上使用流程要求主播身份码。

Tsuk1ko 项目 README 明确说明不再维护普通游客连接模式，改为开放平台连接。对只想点击按钮看弹幕的主播，开发者审核、项目创建和密钥配置不属于低成本使用体验。

## 比替换显示库更需要关注的地方

1. **采集与显示分开判断。** 当前悬浮窗和点歌机依赖 LAPLACE 控制台向本地桥持续广播。更换渲染组件不能解决远端控制台加载或采集失败。
2. **控制台维持后台运行。** 当前主布局使用 `forceMount` 保留控制台页，切换标签不会直接卸载它；关闭应用、账号切换或网页连接失败仍影响事件来源。
3. **优先补主播阅读体验。** 字号调整、表情显示、断线提示和配置同步，比新增整个独立应用的菜单/发布系统更直接满足此任务。置顶、穿透、拖动、位置保存和防 OBS 捕获已有基础实现，应保留。
4. **别引入第二套账号与弹幕连接。** 除非计划整体替换 LAPLACE 采集，显示窗口继续消费现有标准事件，是较低维护成本的边界。

[LAPLACE Event Bridge 官方说明](https://github.com/laplace-live/event-bridge#event-fetcher-bridge-mode) 提到 Event Fetcher v2.2.0+ 的桥模式可不依赖控制台持续打开。但该路径涉及另一个采集服务及部署，适合后续确实需要增强数据源独立性时评估，不建议为了此次显示模块直接加入。

## 建议执行顺序

- 现在保留锁定版本，不做整套替换或升级。
- 按主播实际需求，只补关键的阅读和连接体验；沿用现有 Event Bridge、窗口管理和测试。
- 需要较多样式/事件定制时，再将当前显示部分整理为根项目内部模块；保留来源、版权和许可记录。
- 如果选择直接采用上游新版代码，先按 [升级评估](./chat-overlay-upgrade-assessment.md) 处理许可和适配，再补过滤、设置迁移及跨平台窗口测试。
